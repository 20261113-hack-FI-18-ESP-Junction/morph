# Demonstrating the saved-evidence analyst

This is a real hosted Gemma demonstration using saved simulation. It is an addition to the original Morph demonstration requirements; it does not replace the physical Duplo cycle, Studio/VLA training, Anomalib/OpenVINO, Nemotron observation, Gemini Decision 1 selection or ElevenLabs spoken goal.

Use the task-owned preview whose current addresses are recorded in [services.json](runs/hosted-03/services.json). The colleague's dashboard on port 3001 and records API on 8000 remain separate running processes. The preview uses the current source, an isolated compiled dashboard and an isolated database; it cannot control the arms.

1. Open the preview and choose **Quality & history**. In the bottom source bar choose **Simulation**, then session **Run m16-recovery:session**. Scroll to **Gemma evidence analyst**.
2. Point out the backend cards: **1 / 1 correct cycles**, **1 / 2 successful attempts**, **one retry**, **one recovered cycle**, **zero first-attempt successes**. The denominator for attempts includes the retained failed attempt. A late confirmation revises the original records; it does not add another cycle or erase a failure.
3. Select saved report **561fb240-3ca9-434b-bcef-7bd376b1ed49**. Loading this report makes no inference request. Its first actual Gemma interpretation reads: “The cycle is recorded as correct despite containing two finished attempts: a failed first attempt and a successful second attempt acting as a retry.” This text was returned by the hosted model, not authored as a fixture.
4. Open citation **f003** to inspect `m16-recovery-attempt-1`, revision 1, with its failed outcome. Open **f009** for recorded confirmation, and a correction citation such as **f010** for old/new field values, author and reason. The UI distinguishes captured revisions from the current cycle trace. The unknown cause remains labelled as missing evidence.
5. Show the provenance at the bottom of the report: exact requested/returned model `gemma-4-26b-a4b-it`, prompt `gemma-evidence-v7`, source digest, **11631.86 ms provider latency**, and **21020.94 ms total report time**. Queue time can make these durations differ. They do not change the saved cycle's measured duration.
6. Reload the page or enter **Replay**. The report remains a view of saved data. Canonical exports and event sequence remained unchanged in the recorded Chromium exercise, and browser03 sent zero analysis POSTs.
7. Choose **Compare sessions**, set baseline `m16-recovery:session` and adaptive `gemma-eval-classification-mismatch:session`. The table shows each saved population separately, one cycle per session. Reviewed matching metadata is absent, so compatibility is **unknown** and improvement deltas are withheld. Select saved report **ba5d2c29-9477-41d6-8c3e-b39c1a15bd24**, produced by final prompt v8. Its actual Gemma answer is **insufficient evidence** and states: “Configuration identifiers alone do not establish reviewed matching protocol, population, settings and timing boundaries.” Both cited configuration records can be opened. The measured provider latency was **2819.88 ms**. Selecting sessions or this saved report makes no inference request.

**Generate cycle explanation** and **Generate session comparison** are the explicit actions for new hosted requests. Reopening saved evidence does not repeat a rejected or failed request. Provider errors, local rejection and stale evidence remain visible and distinct.

The browser report's prose cites four of the five required metrics; the zero first-attempt-success count remains visible in the canonical cards. Its headline is imprecise about the role of late confirmation. The earlier actual v6 report `6056fa5c-0c85-474b-916c-16de3f0e2916` cites all five metrics, with one ambiguous audit phrase. Explain these limitations if discussing model quality. The independent agent review scores each useful recovery response at nine supported claims out of ten, with one ambiguous claim; this is not an operator usability study.
